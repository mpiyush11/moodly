# MOODLY — catalogue, login and responsive change report

## Scope

The existing Moodly website is retained. Desktop wordmark, monochrome styling, two-column hero, 2×2 category tiles, 3:4 images, four native product rails, custom-studio panel and editorial footer remain. This is not a Google Sites replacement or a new visual redesign. New request explanations are added using the same design system.

## 1. Catalogue + WhatsApp request flow

- The shopping bag is now a selection list. It can contain several designs; single-item Request via WhatsApp still preserves the other selected items.
- Customer chooses design/colour/size/quantity and delivery preference. Optional city is the only contact-related field.
- No website name/phone/pincode form, customer account, online payment or automatic confirmation.
- `/api/checkout/request` validates IDs/variants/quantity against the current server catalogue, computes an indicative amount on the server, and returns an encoded WhatsApp draft.
- The draft explicitly requests availability, printing feasibility, delivery charges, final amount and dispatch confirmation before payment.
- The API creates no order/customer record and changes no inventory. It does not send a message: the customer must open WhatsApp and tap Send.
- The former public create-order endpoint returns HTTP 410 with the new request endpoint instead of silently reserving blanks. Historic private order records and cancellation tools are retained, not deleted.
- Every product has a stable reference code. Custom print enquiry collects colour, size, quantity, placement and optional city; the artwork is attached privately in WhatsApp, not uploaded to this website.

## 2. Business clarity and lower handling effort

- Catalogue copy uses the supplied 240 GSM specification instead of the agent's 280 GSM template claims. Owner-edited specifications are not globally replaced.
- Removed blanket 48–72-hour dispatch, free-delivery and guaranteed-exchange promises from customer-facing flow. Terms are confirmed in chat.
- Added How it works and request-first information, care/privacy/exchange explanations and no-countdown language.
- Added owner-editable Instagram profile, WhatsApp Business catalogue URL, reply hours and dispatch note in Studio settings.
- Added WhatsApp tools: copy/download greeting, away, custom-brief, confirmation, received-payment and dispatch replies; suggested app labels; before-ad checklist.
- No paid WhatsApp API, chatbot, payment gateway or analytics subscription was introduced.
- WhatsApp Business labels/away messages and Instagram ads cannot be configured from this website without external account access. The tools give usable text and instructions, not a false claim of configuring those accounts.

## 3. Login / origin fixes

- The old origin check trusted only one host header. The new check compares exact origins from the request URL, Host, first forwarded Host, an explicitly configured canonical URL, and the current Codespaces workspace's known forwarded hostname.
- Host rewrites behind trusted local/Codespaces proxies no longer cause false cross-origin rejection.
- Cross-site browser POSTs, unrelated preview workspaces, alternate ports and malformed/null origins remain rejected. No wildcard origin bypass was added.
- Added exact optional `NEXT_PUBLIC_SITE_URL` / `MOODLY_TRUSTED_ORIGINS` configuration; Codespaces derives its own known hostname automatically.
- Fast typing before React hydration previously left visible password text but empty React state. Login now reads the native FormData password and waits for its handler to mount; no password is taken from client props.
- Login success navigates to a fresh protected page; signed HttpOnly cookie checks, wrong-password rejection and logout remain intact. Development password login is still disabled in production; production uses Supabase Auth membership.

## 4. Hydration fixes

- Screenshot annotation `bis_skin_checked` is not generated by the app; it is consistent with a browser/security extension adding DOM attributes before React hydration.
- Added a bounded, attribute-specific pre-hydration cleanup for that known annotation. It stops on mount (or at its safety timeout). No blanket `suppressHydrationWarning`, hidden console errors or removed security attributes.
- Regression test simulates annotation insertion before hydration and verifies login without React mismatch errors.
- Corrected the PDP fieldset/legend nesting and made order-history date formatting explicit in Asia/Kolkata. Footer year is passed from the server so its first client render uses the same value.
- Added the missing local favicon asset.

## 5. Mobile-only responsive changes

- Tighter mobile hero spacing and responsive media height; desktop hero geometry stays unchanged.
- Readable mobile form text (16px), 48px actions, larger colour touch targets, wrapping metadata and safe-area padding.
- Native horizontal rails retain the same product cards and desktop widths; mobile adds a swipe hint.
- Mobile selection/custom-request dialogs fit the viewport and scroll internally.
- Studio gets mobile colour/size stock cards instead of a sideways stock matrix; historical orders use stacked cards on mobile. Desktop tables are retained.
- Footer links/status wrap rather than squeezing at narrow widths.
- Browser checks target 320, 360, 390, 430, 768, 1024, 1440 and 1920px, including overflow, navigation, search, size guide, request draft, custom brief, login, Studio controls and logout.

## Not invented / not yet supplied

- Actual 8–10 print artwork and product photos were not supplied. Existing starter/legacy catalogue images remain; starter imagery is identified as such on PDP. Upload actual photos in Studio before selling.
- No real Instagram profile, WhatsApp catalogue share link, measured garment sizes, guaranteed printer schedule, exchange terms or real stock split was invented.
- The owner mentioned 100 blanks but did not provide their colour/size distribution. Existing starter counts were not randomly redistributed; enter actual quantities in Studio. This is a test catalogue until those details and private production credentials are configured.
- Shared test credentials were retained according to the earlier explicit owner choice. Never store real customer data with this shared test setup.
